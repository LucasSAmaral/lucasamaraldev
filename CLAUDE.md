# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Personal portfolio site for Lucas Amaral, built with Next.js 16 (App Router) and React 19. Content and UI copy are largely in Portuguese; code identifiers and comments are in English/Portuguese mixed as found in the file.

## Commands

```bash
npm run dev       # regenerates generated-config.json, then starts Next.js dev server (--turbopack)
npm run build     # regenerates generated-config.json, then builds for production
npm start         # runs the production build
npm run lint      # BROKEN: runs `next lint`, which was removed in Next.js 16 (see note below)
npm run config    # regenerates generated-config.json only (ts-node src/config/build-config.ts)
npm run release   # cuts a release with release-it (bumps version, commits "Release x.y.z", tags)
npm run cy:open   # shortcut for `cypress open`
```

Node version is pinned via `.nvmrc` (22) and the Dockerfile (`node:22.22-alpine`).

**Lint is currently non-functional**: `next lint` no longer exists in Next.js 16 (running it errors with `Invalid project directory provided, no such directory: .../lint`). The ESLint setup is also out of sync — `.eslintrc.json` extends `next/core-web-vitals`, but `eslint-config-next` is pinned to `15.1.7` and `eslint` to `^8`. Fixing it requires migrating to the ESLint CLI (`eslint .`) with a flat config and an `eslint-config-next` version matching Next 16.

### Tests (Cypress only — no Jest/unit test runner)

- Component tests live next to the components under `tests/` folders as `*.component.cy.tsx` (e.g. `src/app/work-experience/components/tests/ExperienceCard.component.cy.tsx`). Shared test data/helpers, when needed, go in a `tests/helper/` folder. Component testing uses the `next` framework with the **webpack** bundler (`cypress.config.ts`).
- E2E tests live in `cypress/e2e/*.cy.ts` and run against a built/served app (`baseUrl: http://localhost:3000`).

```bash
npx cypress open                              # interactive runner (component or e2e)
npx cypress run --component                   # all component tests, headless
npx cypress run --component --spec "src/app/work-experience/components/tests/ExperienceCard.component.cy.tsx"
npx cypress run --e2e                          # all e2e tests, headless (requires app running/build+start)
npx cypress run --e2e --spec "cypress/e2e/contact-form.cy.ts"
```

CI always runs `npm run build && npm start` before Cypress, then component specs, then e2e specs. `.github/workflows/cypress.yml` runs on pushes to any branch except `main` (and not on tags); `ci-cd.yml` runs on tag pushes (see Releasing).

**`data-cy` attributes**: use the custom `cy.getDataCy('some-id')` command (defined in `cypress/support/commands.ts`) instead of raw `cy.get('[data-cy=...]')` when writing new specs.

## Configuration: the generated-config build step

There is no `.env`-driven runtime config; content and app config are assembled at build/dev time:

- `src/config/build-config.ts` reads `navigation-menu-config.json`, `app-config.json`, `locale/common-locale.json`, `locale/pt.json`, `locale/en.json`, deep-merges them (`merge-options`, later files win), and writes the result to `generated-config.json` at the repo root. The output has three top-level keys: `navigationMenu`, `appConfig` and `locale` (with `locale.commonLocale`, `locale.pt`, `locale.en`).
- Each source file is already wrapped in its own top-level key (e.g. `pt.json` is `{ "locale": { "pt": { ... } } }`, `app-config.json` is `{ "appConfig": { ... } }`) — the merge relies on this, so keep the wrapper when adding new keys.
- `generated-config.json` is gitignored and regenerated by `npm run config` (also runs automatically before `dev`/`build`) — **do not hand-edit it**; edit the source JSON files under `src/config/` instead.
- App code imports `generated-config.json` directly (e.g. `src/app/contact/actions.ts` imports `CONFIG` from `../../../generated-config.json`). If this file is missing, run `npm run config` first.
- Secrets used for the contact form's EmailJS integration (`SERVICE_ID`, `TEMPLATE_ID`, `USER_ID`) live in `.env` and are read via `process.env` in `src/app/contact/actions.ts`; the actual EmailJS API URL comes from `app-config.json` instead of the env file. When `NODE_ENV === 'development'` the action returns early without calling EmailJS, so no email is sent under `npm run dev`.

## i18n

There is no i18n library. `pt.json` / `en.json` under `src/config/locale/` are merged into `generated-config.json` under `locale.pt` / `locale.en`, and components read the string for the currently selected language directly from that object based on `LanguageOptionsContext`'s `selectedLanguage` (`'pt' | 'en'`, defaulting to `'pt'`, overridable via the `?lang=` search param — see `src/app/components/language-options/LanguageOptions.context.tsx`). When adding user-facing copy, add the key to **both** `pt.json` and `en.json` under the same path, and consume it from `generated-config.json`.

## Architecture

- **App Router** under `src/app/`: the home page is `src/app/page.tsx`; other routes have one folder each (`about-me/`, `work-experience/`, `contact/`) with its own `page.tsx` and, where needed, a local `components/` folder for route-specific components. Root-level `template.tsx` and `loading.tsx` provide the per-navigation wrapper and loading fallback.
- **Shared UI** lives in `src/app/components/`. Cross-cutting concerns are implemented as React Context providers, each colocated as a `<Feature>.context.tsx` next to its `<Feature>.component.tsx`:
  - `modal/Modal.context.tsx` + `Modal.container.tsx` — global modal, driven by a state machine (`CLOSED → OPENING → OPENED → CLOSING → CLOSED`) rendered into `#modal` (see `layout.tsx`). Open modals via the `useModal()` hook, not by rendering modal components directly. The container is an accessible dialog (focus trap, Esc closes, focus returns to the opener, body scroll locked); give the heading of any content you open `id={MODAL_TITLE_ID}` (exported by `Modal.container.tsx`) so `aria-labelledby` resolves.
  - `navigation-menu/NavigationMenu.context.tsx` — the mobile menu's open/close status (`navigationMenuMobileStatus`). The `MenuStatus` type (`'CLOSED' | 'CLOSING' | 'OPENED' | 'OPENING'`) is defined in `NavigationMenu.component.tsx`. The active route is not stored in context: menu options compare `usePathname()` with their route and set `aria-current="page"`.
  - `language-options/LanguageOptions.context.tsx` — current language (described above). The selector itself is a segmented PT | EN control (`LanguageOptions.component.tsx`), with no menu state.
  - The header bar (logo, menu, language selector and mobile menu toggle) is `components/Header.component.tsx`, rendered by `template.tsx`.
  - `template.tsx` renders the page structure `<div>` → header, `<main>` (page content, with the ~200ms fade between pages) and `Footer.component.tsx`. The footer is hidden on `/` and `/contact` (`ROUTES_WITHOUT_FOOTER`), because those pages already show the social links in their content.
  - Other shared building blocks: `SocialLinks.component.tsx` (LinkedIn and GitHub icon links; also exports the icons and `getSocialUrls` for reuse), `ActionLink.component.tsx` (Link styled as a button, `$variant` `primary | secondary | tertiary`), `Chip.component.tsx` (`ChipList` + `Chip`, `$variant` `filled | outline`), and `Eyebrow` / `VisuallyHidden` in `styles/styles.ts`.
  - All providers are composed in `src/app/Providers.tsx` (`QueryClientProvider > Suspense > LanguageOptionsProvider > ModalProvider > NavigationMenuProvider`); add new global providers there, innermost-last.
- **Styling** is `styled-components` with SSR support via `src/app/lib/registry.tsx` (`StyledComponentsRegistry`, wraps the app in `layout.tsx`). Global styles are in `src/app/styles/globalStyle.ts`; design tokens (colors, fonts, radii, breakpoints, transitions) are plain constants in `src/app/styles/theme.ts` — import them directly instead of using a `ThemeProvider`, so Cypress component tests (mounted without providers) keep working.
- **File naming convention** (follow this for new files): `Name.component.tsx` (component), `Name.context.tsx` (context/provider), `Name.container.tsx` (container wiring context to render output), plain `helpers.ts`/`actions.ts` for logic. Cypress component specs mirror the component name: `Name.component.cy.tsx` in a sibling `tests/` folder.
- **Server actions**: `'use server'` functions (e.g. `src/app/contact/actions.ts`) are used for backend calls (EmailJS submission) instead of API routes.
- Path alias `@/*` maps to `src/*` (see `tsconfig.json`).

## Formatting

Prettier is configured (`.prettierrc`): single quotes, semicolons, trailing commas, 100 char width, `arrowParens: avoid`. Match this style; there's no separate format script wired up, so rely on editor integration or `npx prettier --write`.

## Releasing

`npm run release` runs `release-it` with its default settings (there is no `.release-it.json` or `release-it` key in `package.json`): it bumps the version in `package.json`/`package-lock.json`, commits as `Release x.y.z`, and creates the `vx.y.z` tag. It does **not** update `CHANGELOG.md` — that file stopped at `0.2.0` (generated by the old `standard-version` setup) and is not maintained anymore.

Commit messages conventionally follow `type: descrição em português` (e.g. `feat:`, `fix:`, `chore:`, `test:`); nothing enforces it, but follow it for new commits.

Pushing a tag triggers `.github/workflows/ci-cd.yml`: Cypress component + e2e → Docker image build/push to `lucassamaral/lucasamaraldev:<tag>` → Vercel production deploy (`vercel build --prod` + `vercel deploy --prebuilt --prod`). Vercel's Git auto-deploy is disabled in `vercel.json` (`git.deploymentEnabled: false`), so production deploys happen only through this tag pipeline.
